# 0002. Event schema and idempotency

## Status

Accepted

## Context

ADR 0001 defines at-least-once delivery; this ADR defines how duplicates are neutralized.

Duplicate events may be produced in two situations:

- Kafka acknowledges the write, but the `202` response is lost and the client retries.
- The consumer crashes after the `INSERT` and before committing the Kafka offset.

Using `key` + timestamp as the idempotency key is not acceptable: different sources may send the same key with the same timestamp, and legitimate readings would be silently discarded.

## Decision

- ID will be generated by the client in the first attempt to send the event and reused in every retry
- UUIDv7 is mandatory. Its time-ordered prefix makes inserts land at the end of the B-tree index, improving locality and reducing page splits. Requiring v7 from the start keeps the contract compatible: relaxing it later does not break clients, while tightening it would.
- If ID is absent or not in UUIDv7, the API responds with status 400 - Bad request
- Schema: see `migrations/0001_create_event.sql`
- The consumer inserts with an explicit conflict target:

```sql
INSERT INTO event (id, key, value, event_time)
VALUES ($1, $2, $3, $4)
ON CONFLICT (id) DO NOTHING;
```

A duplicate is treated as success. Without `ON CONFLICT`, a duplicate raises `23505`, aborts the transaction, the offset is never committed, and the consumer reprocesses the same message forever (poison message). `RowsAffected() == 0` identifies a duplicate and is logged and counted as a metric.
- `event_time` is set by the client; `ingested_at` is set by the database. `ingested_at - event_time` measures end-to-end ingestion latency.

## Consequences

- A client that reuses an ID for a different event loses that event silently.
- Every database constraint must be checked by the API before responding `202`; otherwise poison messages are created in the consumer. The API must reject:
    - empty `key`;
    - `key` longer than 255 characters (Go's `len()` counts bytes, not characters);
    - NUL bytes (`\x00`) in `key`, which PostgreSQL rejects in text columns;
    - `event_time` outside the range PostgreSQL accepts (the API field is `uint64`; PostgreSQL has no unsigned types).
- The accepted window for past and future `event_time` values is still open.
- PostgreSQL error `DETAIL` messages include the offending row; they must not be logged without sanitization.
- `now()` returns the transaction start time, so all events inserted in the same transaction share the same `ingested_at`.
- Integration tests against a real PostgreSQL instance will cover these boundary cases when the consumer is implemented.
